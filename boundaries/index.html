    边界与取舍¶

    conf_base 解决的是「本地进程的配置文件」这一件事。它有意不做很多事，明确列出这些边界，比藏着更有用。

    不是配置中心客户端¶

    没有远程拉取、没有长轮询、没有灰度发布、没有服务端推送。

    需要这些能力时，配置中心（Nacos / Apollo / Consul / etcd）才是正解。可以两者并用：配置中心下发密钥与开关，conf_base 管理本地落盘的配置。

    不适合高频写入¶

    每次赋值默认都落盘（除非包在 batch() 里）。写一次的量级是「一次序列化 + 一次 os.replace」。

    写入频率 是否合适
    启动时读，运行中偶尔改 合适
    每分钟改几次 合适，建议用 batch()
    每秒都在改 不合适——这类数据应该进数据库或缓存

    不适合复杂嵌套模型¶

    配置项只支持 bool / int / float / str / list / dict 六种，且值类型锁定为默认值的类型。没有嵌套的模型校验、没有列表元素类型约束、没有联合类型。

    需要这些时用 pydantic；或者把嵌套结构摊平成多个 section。

    不适合重复结构¶

    若干个同构的子配置（[server.a]、[server.b]…）可以用「多个 Section 实例 + 一个遍历方法」模拟，见 Section 与配置项。但这不是一等公民：没有 List[ServerConfig] 这种写法。

    条目数量动态变化、需要按索引随机访问时，直接把整块存成 dict 类型的单个配置项更省事。

    不适合存大文件¶

    配置文件会被整体读进内存、整体序列化、整体重写。几百 KB 没问题，几 MB 就该考虑别的存储。

    多进程并发只保护「写」¶

    装了 filelock 后，写入会先拿文件锁，避免两个进程同时 os.replace 把文件写坏。但 读不加锁：一个进程正在写、另一个正在读时，读者拿到的是「旧内容」或「新内容」，不会拿到半截文件（os.replace 是原子的），但不保证是最新的。

    需要强一致时，用外部协调（队列、数据库）而不是配置文件。

    不是 pydantic 的替代品¶

    conf_base pydantic / pydantic-settings
    定位 本地配置文件的读写与落盘 数据校验与模型定义
    嵌套模型 不支持 一等公民
    类型系统 六种基础类型 完整类型系统
    序列化 JSON/YAML/TOML 文件 多种格式
    加密落盘 内置 需要自己写

    两者可以共存：用 pydantic 定义接口层的数据模型，用 conf_base 管理需要落盘的本地配置。

    硬约束清单¶

    约束 原因
    配置类不能相互继承 描述符与 ConfigFile 是类级绑定，继承会抢同一个文件
    配置值类型锁定为默认值类型 避免「今天存字符串、明天存数字」的隐性类型漂移
    环境变量覆盖的项禁止回写 覆盖是只读视图，写回会让文件与环境变量冲突
    _format 只接受实例 字符串无法表达「自定义格式」，容易造成两套语义
    密钥只从参数/环境变量读 密钥绝不能进配置文件
